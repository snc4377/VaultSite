As we saw in the previous section, it's often possible to perform a Kerberoast attack across a forest trust. If this is possible in the environment we're assessing, we can execute it with `GetUserSPNs.py` from our Linux attack host. For this, we need credentials for a user who can authenticate to the other domain and specify the `-target-domain` flag in our command. When performing this against the `FREIGHTLOGISTICS.LOCAL` domain, we see an SPN entry for the `mssqlsvc` account.

## Cross-Forest Kerberoasting

#### Using GetUserSPNs.py

```
snchh337@htb$ GetUserSPNs.py -target-domain FREIGHTLOGISTICS.LOCAL INLANEFREIGHT.LOCAL/wley
```

```
snchh337@htb GetUserSPNs.py -request -target-domain FREIGHTLOGISTICS.LOCAL INLANEFREIGHT.LOCAL/wley
```

Then we could try to crack it offline using Hashcat with mode `13100`. If successful, we could authenticate to the `FREIGHTLOGISTICS.LOCAL` domain as a Domain Admin. If we succeed with this type of attack during a real-world assessment, it would also be worth checking if this account exists in our current domain and suffers from password reuse. This could be a quick win for us if we haven't yet managed to escalate privileges in our current domain. Even if we already have control of the current domain, it would be worth adding a finding to our report if we discover password reuse in accounts with similar names across different domains.

Suppose we can perform a Kerberoast attack through a trust relationship and have exhausted our options in the current domain. In that case, it might also be worth attempting a password spraying attack with the cracked password, as there's a chance it could be used for other service accounts if the same administrators manage both domains. Here we have another example of iterative testing and leaving no stone unturned.

## Searching for External Group Membership with Bloodhound-python

As noted in the last section, we occasionally see users or administrators from one domain as members of a group in another domain. Since only `Domain Local Groups` allow users from outside their forest, it's not uncommon to see a privileged user from Domain A as a member of the built-in administrators group in Domain B when dealing with a bidirectional forest trust relationship. If we're testing from a Linux host, we can gather this information using the [Python implementation of BloodHound](https://github.com/fox-it/BloodHound.py). We can use this tool to collect data from multiple domains, load it into the GUI tool, and search for these relationships.

In some assessments, our client may provision us a VM that gets an IP from DHCP and is configured to use the internal domain's DNS. Other times, we'll be on an attack host without DNS configured. In this case, we'd need to edit our `resolv.conf` file to run this tool, as it requires a DNS hostname for the target Domain Controller rather than an IP address. We can edit the file as follows using sudo rights. Here we've commented out the current nameserver entries and added the domain name and IP address of `ACADEMY-EA-DC01` as the nameserver.

#### Adding INLANEFREIGHT.LOCAL Information to /etc/resolv.conf

```
snchh337@htb$ cat /etc/resolv.conf 

# Dynamic resolv.conf(5) file for glibc resolver(3) generated by resolvconf(8)
#     DO NOT EDIT THIS FILE BY HAND -- YOUR CHANGES WILL BE OVERWRITTEN
# 127.0.0.53 is the systemd-resolved stub resolver.
# run "resolvectl status" to see details about the actual nameservers.

#nameserver 1.1.1.1
#nameserver 8.8.8.8
domain INLANEFREIGHT.LOCAL
nameserver 172.16.5.5
```

Once this is in place, we can run it against the target domain as follows:

## Final Thoughts on Trust Relationships

As seen in the previous sections, there are multiple ways to leverage domain trust relationships to gain additional access and even pivot to escalate privileges in our current domain. For example, we can take control of a domain that has a trust relationship with our current domain and find password reuse in privileged accounts. We've seen how Domain Admin rights in a child domain almost always mean we can escalate privileges and compromise the parent domain using the ExtraSids attack. Domain trust relationships are a broad and complex topic. This module's introduction has given us the tools to enumerate trust relationships and perform some standard intra-forest and cross-forest attacks.
