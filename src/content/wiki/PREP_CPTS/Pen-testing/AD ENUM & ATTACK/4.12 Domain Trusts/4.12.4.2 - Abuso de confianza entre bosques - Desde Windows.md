## Kerberoasting Across Forests (Cross-Forest)

Kerberos attacks like Kerberoasting and ASREPRoasting can be performed across trust relationships, depending on the trust direction. In a situation where you're in a domain with an incoming or bidirectional domain/forest trust, you can likely perform several attacks to gain a foothold. Sometimes you can't escalate privileges in your current domain, but you can instead obtain a Kerberos ticket and crack a hash for an administrative user in another domain that has Domain/Enterprise Admin privileges in both domains.

We can use PowerView to enumerate accounts in a target domain that have Service Principal Names (SPNs) associated.

#### Enumerating Accounts with Associated SPNs Using Get-DomainUser

```
PS C:\htb> Get-DomainUser -SPN -Domain FREIGHTLOGISTICS.LOCAL | select SamAccountName

samaccountname
--------------
krbtgt
mssqlsvc
```

We see there's an account with an SPN in the target domain. A quick check shows this account is a member of the Domain Admins group in the target domain, so if we can perform Kerberoasting and crack the hash offline, we'd have full administrator rights in the target domain.

#### Enumerating the mssqlsvc Account

```
PS C:\htb> Get-DomainUser -Domain FREIGHTLOGISTICS.LOCAL -Identity mssqlsvc |select samaccountname,memberof

samaccountname memberof
-------------- --------
mssqlsvc       CN=Domain Admins,CN=Users,DC=FREIGHTLOGISTICS,DC=LOCAL
```
We will perform a Kerberoasting attack through trust using `Rubeus`. We run the tool as we did in the Kerberoasting section, but include the `/domain:` flag and specify the target domain.

#### Performing a Kerberoasting Attack with Rubeus Using the /domain Flag

```
PS C:\htb> .\Rubeus.exe kerberoast /domain:FREIGHTLOGISTICS.LOCAL /user:mssqlsvc /nowrap
```

## Reuse of Administrator Passwords and Group Membership

Occasionally, we'll find ourselves in a situation where there's a bidirectional forest trust managed by administrators from the same company. If we can take control of Domain A and obtain cleartext passwords or NT hashes for the built-in Administrator account (or an account that's part of the Enterprise Admins or Domain Admins group in Domain A), and Domain B has a privileged account with the same name, then it's worth checking for password reuse between the two forests. I've occasionally encountered issues where, for example, Domain A would have a user named `adm_bob.smith` in the Domain Admins group, and Domain B had a user named `bsmith_admin`. Sometimes the user used the same password in both domains, and taking control of Domain A instantly gave me full administrator rights in Domain B.

We may also see users or administrators from Domain A as members of a group in Domain B. Only `Domain Local Groups` allow security principals from outside their forest. We might find a Domain Admin or Enterprise Admin from Domain A as a member of the built-in Administrators group in Domain B in a bidirectional forest trust relationship. If we can take control of this administrator user in Domain A, we'd gain full administrative access to Domain B based on group membership.

We can use PowerView's [Get-DomainForeignGroupMember](https://powersploit.readthedocs.io/en/latest/Recon/Get-DomainForeignGroupMember/) function to enumerate groups with users from outside the domain, also known as `foreign group membership`. Let's test this against the `FREIGHTLOGISTICS.LOCAL` domain with which we have a bidirectional external forest trust.

## SID History Abuse - Across Forests

SID History can also be abused across a forest trust. If a user is migrated from one forest to another and SID Filtering is not enabled, it's possible to add a SID from the other forest, and this SID will be added to the user's token when authenticating through the trust. If the SID of a privileged account in Forest A is added to the SID History attribute of an account in Forest B, assuming they can authenticate across the forest, then this account will have administrative privileges when accessing resources in the associated forest. In the following diagram, we can see an example of the user `jjones` being migrated from the `INLANEFREIGHT.LOCAL` domain to the `CORP.LOCAL` domain in a different forest. If SID filtering is not enabled during this migration and the user has administrative privileges (or any other interesting rights like ACE entries, share access, etc.) in the `INLANEFREIGHT.LOCAL` domain, they will retain their administrative rights/access in `INLANEFREIGHT.LOCAL` while being a member of the new domain, `CORP.LOCAL`, in the second forest.

> ### 🔍 Attack Context
> We start with a regular user in a domain with no special privileges (`INLANEFREIGHT`). 
> 1. We look for trust relationships (incoming or bidirectional):
>    ```powershell
>    Get-ADTrust -Filter *
>    ```
> 2. We execute the attack with Rubeus against the target domain (`FREIGHTLOGISTICS.LOCAL`):
>    ```powershell
>    .\Rubeus.exe kerberoast /domain:FREIGHTLOGISTICS.LOCAL /user:mssqlsvc /nowrap
>    ```
> 
> ---
> 
> ### 🛡️ HTB Coach's Explanation
> Your observation is very accurate. **No special permissions** are needed to perform Kerberoasting. It's not a bug, but an exploitation of Active Directory and Kerberos' fundamental design.
> 
> #### 1. Why does it work without privileges?
> * **Universal right to TGS:** Any authenticated user (even the most basic) can request a Service Ticket (TGS) for any SPN in their domain to access resources (files, databases, etc.).
> * **Trust extension:** When a trust relationship exists, Domain A tells its Domain Controller (DC): *"I trust Domain B. If my users request resources there, facilitate the process for them."*
> 
> #### 2. The Request Flow (Step by Step)
> ```
> [User] ──(1) Requests ticket for mssqlsvc ──> [Local DC (A)]
> [User] <──(2) Returns Referral Ticket ─── [Local DC (A)]
> [User] ──(3) Presents Referral Ticket ───> [Remote DC (B)]
> [User] <──(4) Returns TGS (Encrypted hash) ─ [Remote DC (B)]
> ```
> * The DC of Domain B verifies the trust and issues the TGS.
> * **The vulnerability:** The delivered TGS is encrypted with the service account's (`mssqlsvc`) password hash. Once you have it, you can extract and attempt to crack it offline (e.g., with Hashcat).
> 
> ---
> 
> ### ⚡ Enumeration vs. Request (Clarification on Rubeus)
> There's a key technical distinction in the process:
> * **Enumerate/List (LDAP):** Tools like PowerView (`Get-DomainUser`) read the directory via LDAP. By default, any valid user (even through a trust) has read permissions to see which accounts have an SPN.
> * **Request/Attack (Kerberos):** When you run Rubeus targeting a user, you're not just "listing"; you're generating the legitimate Kerberos request described above to obtain their ticket. This action never requires advanced privileges.
> 
> > [!warning] Conclusion
> > The entire process relies on legitimate Active Directory functions. The real danger lies in the service account (`mssqlsvc`) using a **weak password**, allowing the obtained ticket to be easily cracked offline.
