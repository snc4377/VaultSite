If we try to analyze all this data during a time-boxed assessment, we'll likely never finish reviewing it or find anything interesting before the assessment ends. However, there's a way to use a tool like PowerView more effectively: by performing targeted enumeration starting from a user we control. Let's focus on the user `wley`, which we obtained after solving the last question in the `LLMNR/NBT-NS Poisoning - from Linux` section. We'll investigate whether this user has any interesting ACL rights we can exploit. First, we need to get our target user's SID to search efficiently.

```
PS C:\htb> Import-Module .\PowerView.ps1
PS C:\htb> $sid = Convert-NameToSid wley
```

Next, we can use the `Get-DomainObjectACL` function to perform our targeted search. In the following example, we are using this function to find all domain objects over which our user has rights, mapping the user's SID via the `$sid` variable to the `SecurityIdentifier` property, which tells us _who_ has the given right over an object. An important thing to note is that if we search without the `ResolveGUIDs` flag, we will see results like the ones below, where the `ExtendedRight` right does not give us a clear idea of which ACE entry the user `wley` has over `damundsen`. This is because the `ObjectAceType` property is returning a GUID value that is not human-readable.

Keep in mind that this command will take some time to execute, especially in a large environment. It may take 1-2 minutes to get a result in our lab.

PS C:\htb> Get-DomainObjectACL -Identity * | ? {$_.SecurityIdentifier -eq $sid}

We could search Google for the GUID value `00299570-246d-11d0-a768-00aa006e0529` and find [this](https://docs.microsoft.com/en-us/windows/win32/adschema/r-user-force-change-password) page showing that the user has the right to force another user's password change. Alternatively, we could perform a reverse lookup using PowerShell to map the right's name back to the GUID value.

Note that if PowerView has already been imported, the cmdlet shown below will produce an error. Therefore, we may need to run it from a new PowerShell session.

#### Performing a Reverse Lookup and Mapping to a GUID Value

```
PS C:\htb> $guid= "00299570-246d-11d0-a768-00aa006e0529"
PS C:\htb> Get-ADObject -SearchBase "CN=Extended-Rights,$((Get-ADRootDSE).ConfigurationNamingContext)" -Filter {ObjectClass -like 'ControlAccessRight'} -Properties * |Select Name,DisplayName,DistinguishedName,rightsGuid| ?{$_.rightsGuid -eq $guid} | fl

Name              : User-Force-Change-Password
DisplayName       : Reset Password
DistinguishedName : CN=User-Force-Change-Password,CN=Extended-Rights,CN=Configuration,DC=INLANEFREIGHT,DC=LOCAL
rightsGuid        : 00299570-246d-11d0-a768-00aa006e0529

```

This gave us our answer, but it would be very inefficient during an assessment. PowerView has the `ResolveGUIDs` flag, which does exactly this for us. Notice how the output changes when we include this flag to display the human-readable format of the `ObjectAceType` property as `User-Force-Change-Password`.

`Why did we review this example when we could have used ResolveGUIDs from the start?`

It's essential that we understand what our tools do and have alternative methods in our toolbox in case a tool fails or gets blocked. Before moving forward, let's take a quick look at how we could do this using the cmdlets [Get-Acl](https://docs.microsoft.com/en-us/powershell/module/microsoft.powershell.security/get-acl?view=powershell-7.2) and [Get-ADUser](https://docs.microsoft.com/en-us/powershell/module/activedirectory/get-aduser?view=windowsserver2022-ps) that we might find available on a client system. Knowing how to perform this type of search without using a tool like PowerView is highly beneficial and could set us apart from our peers. We might be able to use this knowledge to achieve results when a client makes us work from one of their systems and we're restricted to the tools available on that system without the ability to bring any of our own.

This example isn't very efficient, and the command may take a long time to execute, especially in a large environment. It will take much longer than the equivalent command using PowerView. In this command, we first created a list of all domain users with the following command:

Now we can see that our user `damundsen` has `GenericWrite` privileges over the group `Help Desk Level 1`. This means, among other things, that we can add any user (or ourselves) to this group and inherit any rights applied to this group. A search for the rights granted to this group doesn't return anything interesting.

Let's see if this group is nested within other groups, remembering that membership in nested groups means any user in group A will inherit all rights from any group where group A is nested (of which it is a member). A quick search shows that the `Help Desk Level 1` group is nested within the `Information Technology` group, meaning we can obtain any rights that the `Information Technology` group grants to its members if we simply add ourselves to the `Help Desk Level 1` group where our user `damundsen` has `GenericWrite` privileges.

#### Investigating the Help Desk Level 1 group with Get-DomainGroup

```
PS C:\htb> Get-DomainGroup -Identity "Help Desk Level 1" | select memberof

memberof

CN=Information Technology,OU=Security Groups,OU=Corp,DC=INLANEFREIGHT,DC=LOCAL

```

This is a lot to digest! Let's recap where we are:

- We have control over the user `wley` whose hash we previously recovered in the module (assessment) using Responder and cracked offline using Hashcat to reveal the cleartext password value.
- We enumerated the objects that the user `wley` has control over and discovered we could force a password change for the user `damundsen`.
- From here, we found that the user `damundsen` can add a member to the `Help Desk Level 1` group using `GenericWrite` privileges.
- The `Help Desk Level 1` group is nested within the `Information Technology` group, which grants members of that group any rights provisioned to the `Information Technology` group.

Now let's look around and see if members of `Information Technology` can do anything interesting. Again, when performing our search using `Get-DomainObjectACL`, it shows that members of the `Information Technology` group have `GenericAll` rights over the user `adunn`, meaning we could:

- Modify group membership
- Force a password change
- Perform a targeted Kerberoasting attack and attempt to crack the user's password if it's weak

1. **ACL (Access Control List) Enumeration**
    
    - **What it is:** The process of inspecting Access Control Lists (ACLs) on Active Directory objects (such as users, groups, and computers) to discover who has what permissions over them.
    - **Why it matters:** Misconfigured ACLs are a common source of privilege escalation. By enumerating them, a pentester can find "attack paths"—a series of permissions that can be chained to escalate from a low-privileged user to a high-privileged one, such as a Domain Administrator.
2. **Targeted vs. Broad Enumeration**
    
    - The section demonstrates that running a broad query like `Find-InterestingDomainAcl` produces a massive amount of data that's difficult to analyze effectively.
    - A more practical approach is **targeted enumeration**, where you start with a user you control (like `wley` in the example) and specifically search for objects over which _that user_ has rights. This is done using `Get-DomainObjectACL` with a filter for the user's SID.
3. **Chaining ACL Privileges**
    
    - This is the core idea of the section. A single permission may not be enough, but they can often be "chained." The example attack path is:
        1. User `wley` has `ForceChangePassword` rights over user `damundsen`.
        2. `damundsen` has `GenericWrite` rights over the `Help Desk Level 1` group, allowing you to add users to it.
        3. This group is a member of the `Information Technology` group, so you inherit its rights.
        4. The `Information Technology` group has `GenericAll` rights over user `adunn`.
        5. Finally, `adunn` has DCSync rights, allowing domain compromise.
4. **Manual Enumeration (PowerView) vs. Visual Enumeration (BloodHound)**
    
    - **PowerView:** A powerful tool for manually querying ACLs from the command line. Requires you to piece together the attack path step by step, but is essential for understanding what the tools do under the hood. The `-ResolveGUIDs` parameter is crucial for making the output human-readable.
    - **BloodHound:** A graphical tool that automates the discovery of these complex ACL attack paths. It visualizes relationships between objects, making it incredibly fast and easy to see the full privilege chain you painstakingly enumerated using PowerView. In short, it connects the dots for you.
