For security reasons, not all users and machines in an AD environment can access all objects and files. These types of permissions are controlled through Access Control Lists (ACLs). A slight misconfiguration in an ACL can leak permissions to other objects that don't need them, posing a serious threat to the domain's security posture.

---

## Access Control List (ACL) Overview

At their simplest, ACLs are lists that define a) who has access to which asset/resource and b) the level of access they've been provisioned. The configurations themselves in an ACL are called `Access Control Entries` (`ACEs`). Each ACE corresponds to a user, group, or process (also known as security principals) and defines the rights granted to that security principal. Every object has an ACL but may have multiple ACEs because multiple security principals can access objects in AD. ACLs can also be used to audit access within AD.

There are two types of ACLs:

1. `Discretionary Access Control List` (`DACL`) - defines which security principals are granted or denied access to an object. DACLs are composed of ACEs that allow or deny access. When someone attempts to access an object, the system checks the DACL to see the permitted access level. If no DACL exists for an object, full rights are granted to anyone attempting to access it. If a DACL exists but has no ACE entries specifying specific security settings, the system will deny access to all users, groups, or processes attempting to access it.
2. `System Access Control Lists` (`SACL`) - allow administrators to log access attempts made to protected objects.

## Access Control Entries (ACEs)

As mentioned earlier, Access Control Lists (ACLs) contain ACEs that name a user or group and the level of access they have over a given securable object. There are `three` main types of ACEs that can be applied to all securable objects in AD:

|**ACE**|**Description**|
|---|---|
|`Deny Access ACE`|Used within a DACL to show that a user or group is explicitly denied access to an object|
|`Allow Access ACE`|Used within a DACL to show that a user or group is explicitly granted access to an object|
|`System Audit ACE`|Used within a SACL to generate audit logs when a user or group attempts to access an object. Records whether access was granted or not and what type of access occurred|

Each ACE consists of the following `four` components:

1. The security identifier (SID) of the user/group with access to the object (or the security principal's name graphically)
2. A flag denoting the ACE type (Deny, Allow, or System Audit ACE)
3. A set of flags specifying whether child containers/objects can inherit the given ACE entry from the parent or primary object
4. An [access mask](https://docs.microsoft.com/en-us/openspecs/windows_protocols/ms-dtyp/7a53f60e-e730-4dfe-bbe9-b21b62eb790b?redirectedfrom=MSDN), which is a 32-bit value defining the rights granted to an object

## Why Are ACEs Important?

Attackers use ACEs to expand their access or establish persistence. These can be highly useful for us as pen testers, as many organizations are unaware of the ACEs applied to each object or the impact they can have if misapplied. They cannot be detected by vulnerability scanning tools and often go unnoticed for many years, especially in large, complex environments. During an assessment where the client has addressed all the more obvious AD flaws/misconfigurations, ACL abuse can be an excellent way to move laterally/vertically and even achieve total domain compromise. Below are some examples of Active Directory object security permissions. These can be enumerated (and visualized) using a tool like BloodHound, and all are exploitable with PowerView, among other tools:

- `ForceChangePassword` exploited with `Set-DomainUserPassword`
- `Add Members` exploited with `Add-DomainGroupMember`
- `GenericAll` exploited with `Set-DomainUserPassword` or `Add-DomainGroupMember`
- `GenericWrite` exploited with `Set-DomainObject`
- `WriteOwner` exploited with `Set-DomainObjectOwner`
- `WriteDACL` exploited with `Add-DomainObjectACL`
- `AllExtendedRights` exploited with `Set-DomainUserPassword` or `Add-DomainGroupMember`
- `AddSelf` exploited with `Add-DomainGroupMember`

In this module, we'll cover enumerating and leveraging four specific ACEs to highlight the power of ACL attacks:

- [ForceChangePassword](https://bloodhound.specterops.io/resources/edges/force-change-password#forcechangepassword) - grants us the right to reset a user's password without first knowing their password (should be used with caution and typically requires consulting our client before resetting passwords).
- [GenericWrite](https://bloodhound.specterops.io/resources/edges/generic-write#genericwrite) - grants us the right to write to any unprotected attribute of an object. If we have this access over a user, we could assign them an SPN and perform a Kerberoasting attack (which depends on the target account having a weak password set). Over a group, it means we could add ourselves or another security principal to a specific group. Finally, if we have this access over a computer object, we could perform a Resource-Based Constrained Delegation attack, which is outside the scope of this module.
- [AddSelf](https://bloodhound.specterops.io/resources/edges/add-self#addself) - shows the security groups a user can add themselves to.
- [GenericAll](https://bloodhound.specterops.io/resources/edges/generic-all#genericall) - grants us full control over a target object. Again, depending on whether this is granted over a user or group, we could modify group membership, force a password change, or perform a targeted Kerberoasting attack. If we have this access over a computer object and [Local Administrator Password Solution (LAPS)](https://www.microsoft.com/en-us/download/details.aspx?id=46899) is in use in the environment, we can read the LAPS password and gain local administrator access to the machine, which can aid in lateral movement or privilege escalation in the domain if we can obtain privileged controls or some form of privileged access.

In the following sections, we'll primarily cover enumeration and execution of these attacks from a Windows attack host, with mentions of how these attacks could be performed from Linux. Occasionally, we'll encounter many other interesting ACEs (privileges) in Active Directory. In this case, tools like [GMSAPasswordReader](https://github.com/rvazarkar/GMSAPasswordReader) could be used, along with other methods, to obtain the service account's password. Other times, we might find extended rights like [Unexpire-Password](https://learn.microsoft.com/en-us/windows/win32/adschema/r-unexpire-password) or [Reanimate-Tombstones](https://learn.microsoft.com/en-us/windows/win32/adschema/r-reanimate-tombstones) using PowerView and have to research a bit to discover how to exploit them for our benefit. It's worth familiarizing yourself with all [BloodHound edges](https://bloodhound.specterops.io/resources/edges/overview) and as many [Active Directory Extended Rights](https://learn.microsoft.com/en-us/windows/win32/adschema/extended-rights) as possible, since you never know when you might encounter a less common one during an assessment.

## ACL Attacks in Real-World Environments

We can use ACL attacks for:

- Lateral movement
- Privilege escalation
- Persistence

Some common attack scenarios may include:

|Attack|Description|
|---|---|
|`Abusing forgotten password permissions`|Help Desk and other IT staff are often granted permissions to perform password resets and other privileged tasks. If we can take control of an account with these privileges (or an account in a group that confers these privileges to its users), we may be able to perform a password reset for a more privileged account in the domain.|
|`Abusing group membership management`|It's also common to see Help Desk staff and other employees who have the right to add/remove users from a specific group. It's always worth enumerating this further, as sometimes we can add an account we control to a built-in privileged AD group or a group that grants us some interesting privilege.|
|`Excessive user rights`|We also commonly see user, computer, and group objects with excessive rights that a client is likely unaware of. This could occur after installing some software (Exchange, for example, adds many ACL changes to the environment during installation) or some legacy or accidental configuration that grants unintended rights to a user. Sometimes, we can take control of an account that was given certain rights for convenience or to resolve a persistent issue more quickly.|

There are many other possible attack scenarios in the world of Active Directory ACLs, but these three are the most common. We'll cover how to enumerate these rights in various ways, perform the attacks, and clean up what we've done.

**Note:** Some ACL attacks may be considered "destructive," such as changing a user's password or making other modifications within a client's AD domain. When in doubt, it's always better to consult with our client about a specific attack before performing it to have written documentation of their approval in case issues arise. We should always carefully document our attacks from start to finish and revert any changes. This data should be included in our report, but we should also clearly highlight any changes we make so the client can verify that our changes were properly reverted.

## What is WriteDACL?

**WriteDACL** is an ACE (Access Control Entry) that allows you to **modify the DACL (Discretionary Access Control List)** of an object in Active Directory.

Having it over an object means you can **grant yourself any other permission** over that object, which in practice equates to full control over it.

> **Basic flow:** `WriteDACL` → _Grant Rights_ (grant yourself a new ACE) → exploit the obtained ACE

---

## Key Concepts

### Grant Rights

Not an ACE. It's the **action** of leveraging WriteDACL to insert a new ACE into the target object's DACL. It's the intermediate step between having WriteDACL and being able to attack.

### ANY

Diagram notation indicating a **logical OR**: any of the following paths are valid. Not a technical AD term.

---

## Attack Tree

```
WriteDACL
│
├── [ANY] → Grant Rights
│   │
│   ├── GenericWrite
│   │   ├── WriteProperty  → técnicas sobre atributos pasivos
│   │   └── Self           → operaciones auto-referenciales
│   │
│   ├── GenericAll         → superconjunto (incluye todo lo anterior)
│   │   └── AllExtendedRights
│   │       ├── AddMember
│   │       ├── ForceChangePassword
│   │       ├── ReadLAPSPassword
│   │       ├── ReadGMSAPassword
│   │       └── DCSync
│   │
│   └── WriteOwner
│       └── [ANY] → Grant Ownership / Owns Object
```

## GenericWrite

Permission that allows **writing to object attributes**. Has two abuse modes:

### WriteProperty

Writing to **passive attributes** of the object. You modify the data and the system uses it later.

|Technique|Linux|Windows|
|---|---|---|
|Kerberos RBCD|`rbcd.py` / `ntlmrelayx.py`|`Set-DomainObject`|
|SPN-Jacking|Impacket Scripts|PowerView & Rubeus|
|Shadow Credentials|`pyWhisker.py`|Whisker|
|Logon Script|n/a|`Set-DomainObject`|
|Targeted Kerberoasting|`targetKerberoast.py`|`Set-DomainObject`|
|Evil GPOs|`pyGPOabuse.py`|`New-GPOImmediateTask`|

### Self

Special permission that allows **self-referential operations**: performing actions "on yourself" relative to the object, without needing to modify arbitrary attributes.

Most common example: adding yourself as a member of a group.

---

## GenericAll

The most powerful ACE. It's the **superset** of all previous ones:

`GenericAll = GenericWrite + AllExtendedRights + WriteProperty + Self + more`

When you grant yourself GenericAll via WriteDACL, you get immediate access to **all** attack vectors without having to choose.

---

## AllExtendedRights

Enables extended rights over the object. Can be accessed directly or as part of GenericAll.

|Technique|Linux|Windows|
|---|---|---|
|AddMember|`pth-net rpc group addmem` / `ntlmrelayx.py`|`Add-DomainGroupMember` / `net group`|
|ForceChangePassword|`pth-net rpc password`|`Set-DomainUserPassword`|
|ReadLAPSPassword|`LAPSDumper.py` / `CrackMapExec`|`Get-ADComputer`|
|ReadGMSAPassword|`gMSADumper.py` / `ntlmrelayx.py`|`Get-ADServiceAccount`|
|DCSync|`secretsdump.py`|`mimikatz`|

> ⚠️ **DCSync** allows dumping the hashes of **all domain users**, including `krbtgt`. It's total escalation.

---

## WriteOwner

With WriteDACL you can also grant yourself **WriteOwner**, which lets you become the **object's owner**.

The owner can freely modify the DACL → **escalation loop**:

```
WriteOwner → eres propietario → modificas DACL → te das GenericAll → control total
```

## Typical Pentest Flow

1. **BloodHound** detects you have `WriteDACL` on a privileged object (group, user, GPO...)
2. Use `Add-DomainObjectAcl` to grant yourself `GenericAll` on that object
3. Depending on the target:
    - For a **group** → add yourself as a member (`AddMember`)
    - For a **user** → change their password (`ForceChangePassword`)
    - For the **domain** → execute `DCSync` to obtain the `krbtgt` hash
4. With the `krbtgt` hash → **Golden Ticket** → complete domain persistence
