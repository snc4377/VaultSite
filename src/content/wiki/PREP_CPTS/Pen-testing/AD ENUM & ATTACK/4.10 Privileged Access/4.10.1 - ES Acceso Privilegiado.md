Once we gain a foothold in the domain, our objective shifts to advancing our position by moving laterally or vertically to access other hosts and ultimately achieve domain compromise or another goal, depending on the assessment's purpose. To accomplish this, there are several ways we can move laterally. Typically, if we gain control of an account with local administrator rights on a host or a group of hosts, we can perform a `Pass-the-Hash` attack to authenticate via the SMB protocol.

`But what if we don't yet have local administrator rights on any host in the domain?`

There are several other ways we can move through a Windows domain:

- `Remote Desktop Protocol` (`RDP`) - a remote access/management protocol that gives us access to the GUI of a target host  
- [PowerShell Remoting](https://docs.microsoft.com/en-us/powershell/scripting/learn/ps101/08-powershell-remoting?view=powershell-7.2) - also known as PSRemoting or Windows Remote Management (WinRM), a remote access protocol that allows us to execute commands or enter an interactive command-line session on a remote host using PowerShell  
- `MSSQL Server` - an account with sysadmin privileges on a SQL Server instance can log in remotely and execute queries against the database. This access can be used to run OS commands in the context of the SQL Server service account through various methods  

We can enumerate this access in several ways. The easiest, once again, is through BloodHound, as the following edges exist to show us what types of remote access privileges a given user has:

- [CanRDP](https://bloodhound.specterops.io/resources/edges/can-rdp)  
- [CanPSRemote](https://bloodhound.specterops.io/resources/edges/can-ps-remote)  
- [SQLAdmin](https://bloodhound.specterops.io/resources/edges/sql-admin)  

We can also enumerate these privileges using tools like PowerView and even built-in tools.

## Remote Desktop

Typically, if we control a local administrator user on a given machine, we can access it via RDP. Sometimes, we'll gain a foothold with a user who doesn't have local administrator rights anywhere but does have rights to connect via RDP to one or more machines. This access could be extremely useful, as we could leverage the position on the host to:

- Launch further attacks  
- Potentially escalate privileges and obtain credentials for a higher-privileged user  
- Potentially loot the host for sensitive data or credentials  

Using PowerView, we could use the [Get-NetLocalGroupMember](https://powersploit.readthedocs.io/en/latest/Recon/Get-NetLocalGroupMember/) function to start enumerating members of the `Remote Desktop Users` group on a given host. Let's examine the `Remote Desktop Users` group on the `MS01` host in our target domain.

#### Enumerating the Remote Desktop Users Group

```
PS C:\htb> Get-NetLocalGroupMember -ComputerName ACADEMY-EA-MS01 -GroupName "Remote Desktop Users"

ComputerName : ACADEMY-EA-MS01
GroupName    : Remote Desktop Users
MemberName   : INLANEFREIGHT\Domain Users
SID          : S-1-5-21-3842939050-3880317879-2865463114-513
IsGroup      : True
IsDomain     : UNKNOWN
```

From the information above, we can see that all Domain Users (i.e., `all` domain users) can connect via RDP to this host. This is commonly seen on Remote Desktop Services (RDS) hosts or hosts used as jump hosts. This type of server could be heavily used, and we might potentially find sensitive data (such as credentials) that could be used to advance our access, or we might find a local privilege escalation vector that could lead to local administrator access and the theft of credentials/takeover of the account for a more privileged user in the domain. Typically, the first thing I check after importing BloodHound data is:

Does the Domain Users group have local administrator rights or execution rights (such as RDP or WinRM) on one or more hosts?

#### Checking Local Administrator and Execution Rights for the Domain Users Group Using BloodHound

If we gain control of a user through an attack like LLMNR/NBT-NS Response Spoofing or Kerberoasting, we can search for the username in BloodHound to check what type of remote access rights they have, either directly or inherited through group membership, in the `Node Info` tab under `Execution Rights`.

#### Checking Remote Access Rights Using BloodHound

![Node information for WLEY@INLANEFREIGHT.LOCAL showing execution rights, including Delegated RDP Privileges by Group set to 1.](https://cdn.services-k8s.prod.aws.htb.systems/content/modules/143/execution_rights.png)

We could also review the `Analysis` tab and run the predefined queries `Find Workstations where Domain Users can RDP` or `Find Servers where Domain Users can RDP`. There are other ways to enumerate this information, but BloodHound is a powerful tool that can help us quickly and accurately narrow down these types of access rights, which is immensely beneficial for us as pentesters under the time constraints of the assessment period. This can also be useful for the blue team to periodically audit remote access rights across the environment and detect large-scale issues, such as all Domain Users having unintended access to a host or auditing the rights of specific users/groups.

To test this access, we can use a tool like `xfreerdp` or `Remmina` from our VM or the Pwnbox, or `mstsc.exe` if attacking from a Windows host.

## WinRM

Just like with RDP, we might find that a specific user or an entire group has WinRM access to one or more hosts. This could also be low-privileged access that we could use to search for sensitive data or attempt privilege escalation, or it could result in local administrator access, which could be leveraged to advance our access. We can again use PowerView's `Get-NetLocalGroupMember` function for the `Remote Management Users` group. This group has existed since the days of Windows 8/Windows Server 2012 to allow WinRM access without granting local administrator rights.

#### Enumerating the Remote Management Users Group

```
PS C:\htb> Get-NetLocalGroupMember -ComputerName ACADEMY-EA-MS01 -GroupName "Remote Management Users"

ComputerName : ACADEMY-EA-MS01
GroupName    : Remote Management Users
MemberName   : INLANEFREIGHT\forend
SID          : S-1-5-21-3842939050-3880317879-2865463114-5614
IsGroup      : False
IsDomain     : UNKNOWN
```

We can also use this custom `Cypher` query in BloodHound to search for users with this type of access. This can be done by pasting the query into the `Raw Query` box at the bottom of the screen and pressing enter.

```
MATCH p1=shortestPath((u1:User)-[r1:MemberOf*1..]->(g1:Group)) MATCH p2=(u1)-[:CanPSRemote*1..]->(c:Computer) RETURN p2
```

## SQL Server Administrator

Most of the time, we will encounter SQL servers in the environments we face. It is common to find user and service accounts configured with sysadmin privileges on a given SQL server instance. We can obtain credentials for an account with this access through Kerberoasting (common) or others like LLMNR/NBT-NS Response Spoofing or password spraying. Another way you can find SQL server credentials is by using the tool [Snaffler](https://github.com/SnaffCon/Snaffler) to find web.config files or other types of configuration files that contain SQL server connection strings.

BloodHound, once again, is a great bet for finding this type of access through the `SQLAdmin` edge. We can search for `SQL Admin Rights` in the `Node Info` tab for a specific user or use this custom Cypher query to search:


`MATCH p1=shortestPath((u1:User)-[r1:MemberOf*1..]->(g1:Group)) MATCH p2=(u1)-[:SQLAdmin*1..]->(c:Computer) RETURN p2`

Here we see that a user, `damundsen`, has `SQLAdmin` rights over the host `ACADEMY-EA-DB01`.

#### Running mssqlclient.py Against the Target

1. **Basic Connection**  
   ```bash
   python3 mssqlclient.py DOMAIN/user:password@10.10.10.10
   ```

2. **With Windows Authentication**  
   ```bash
   python3 mssqlclient.py -windows-auth DOMAIN/user:password@10.10.10.10
   ```

3. **Common Errors**  
   - `Login failed for user`: Incorrect credentials.
   - `Named Pipes Provider: Could not open a connection to SQL Server`: The server may not have TCP/IP connections enabled.

4. **Post-Connection Commands**  
   - Check user privileges:  
     ```sql
     SELECT IS_SRVROLEMEMBER('sysadmin')
     ```
   - Enable `xp_cmdshell` if you have sufficient privileges:  
     ```sql
     EXEC sp_configure 'show advanced options', 1;
     RECONFIGURE;
     EXEC sp_configure 'xp_cmdshell', 1;
     RECONFIGURE;
     ```
   - Execute OS commands:  
     ```sql
     EXEC xp_cmdshell 'whoami'
     ```

5. **Alternative: Impersonation**  
   If you can impersonate a high-privilege user:  
   ```sql
   EXECUTE AS LOGIN = 'sa';
   EXEC xp_cmdshell 'whoami';
   ```
